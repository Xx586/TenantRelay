# 15 练习题、面试与简历

## 本章解决什么问题

把“看懂代码”变成“能动手、能解释、能经得起追问”，并生成可信的简历表达。

## 小白类比

看游泳视频不等于会游泳；只有亲手改、测、解释过，技术才真正属于你。

## 前置知识

完成前 14 章，至少独立跑通一次 `/chat` 和工单创建/查询。

## 源码阅读顺序

重走 `api/main.py` → `core/intent_recognizer.py` → `scenarios/saas/orchestrator.py` → `scenarios/saas/tools.py` → `store.py` 的主链路，每读一层就画出输入与输出。

## 核心类和函数解释

用五个关键点复述项目：`IntentRecognizer.recognize()` 决定“什么问题”，`SaaSAgentOrchestrator` 决定“谁主责”，Agent 工具白名单决定“能做什么”，`SaaSStore` 决定“真实数据在哪里”，Trace/Monitor 说明“结果如何产生”。

## 一次真实输入如何流转

面试官给出“Webhook 失败并要求建工单”→你说明脱敏和租户认证→解释 Incident 主 Agent、Integration/Ticket 辅 Agent→说明状态白名单和幂等写入→用 Trace 与数据库记录证明结果。

## 可执行实验

1. 新增一个 `rate_limit_inquiry` 意图，补齐模板、路由和 15 条测试数据。
2. 为服务状态工具增加 Mock HTTP 测试，验证不会返回白名单 URL。
3. 记录实际评测结果，查找最差的两类意图并修正。

## 常见错误

把“使用了某技术”当成成果；写没有实测的准确率和延迟；无法解释为什么需要租户过滤、幂等和脱敏。

## 自测题及答案

问：这个项目最值得讲的工程亮点是什么？答：不是“调了大模型”，而是在多 Agent 编排中实现场景隔离、租户安全、真实工具、幂等工单和可观测链路。

## 面试表达

简历可写：“在保持原客服场景兼容的前提下，设计 B2B SaaS 场景开关与五角色 Agent 编排，接入租户隔离 RAG、PostgreSQL 业务查询和幂等工单适配器，实现脱敏 Trace 与工具审计。”指标仅补充实际跑出的数字。
